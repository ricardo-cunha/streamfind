## 2. Resolve workflow inputs consistently for fresh results, cache hits, and reopened projects

The current-run branch checks both `kind` and `representation` for tables, checks only `representation` for JSON, and catches all exceptions by substituting the original descriptor. A JSON parameter gets its decoded value. An ordinary result port gets its descriptor or typed input reference as required by the consumer.
2. Read kind, format, and availability from the published manifest. Preserve the difference between a file locator, a result ID, a JSON string, an explicitly null value, and an absent field. Include node ID, source port, target port, and result ID in resolution errors. Test the generic `anyTable` match with a producer exposing multiple outputs.
3. Inventory, status polling, and graph input lookup should be able to operate on metadata. Trace app users of inline `payload` before making hydration lazy. Move callers that actually need JSON data to a selected-result read in the same change. Preserve JSON viewers and avoid reading large unrelated JSON files while holding the service-wide project mutex.
4. Inspect `streamfind.write_json` in `cpp/core/src/operations/operations.cpp`. It rejects null and reparses string payloads. Serialize a typed JSON value once at the export boundary. Apply the same rule to `artifactDisplay.ts` and test literal text that also happens to be valid JSON syntax.

**Acceptance** — Feed the same table and JSON parameter into a downstream node immediately after production, after an upstream cache hit, and after closing and reopening the project. Compare effective input values and computation keys. Delete or corrupt a fixture payload and verify a diagnostic instead of a descriptor passed as a parameter. Compare the JSON export, MCP response, and viewer for `"null"`, `"42"`, `"{\"x\":1}"`, actual null, and an object.

**Progress** — Parameter resolution now checks the published result kind before looking at the file payload locator, produces a table reference for table results, and preserves JSON strings and explicit JSON null. Table parameter references retain `result_id`, the actual source output port, producer identity, and the service-owned `result:<id>` locator. ## 3. Make result lineage uniform and registry publication atomic

**Confirmed in source**

- `dynamic_plugin_manager.cpp`, `invoke_dynamic`, around lines 148, 347, and 462. Table publication serializes tuples as positional arrays. JSON publication turns the same tuples into named objects.
- `Project::register_result_manifest`, around line 2942, consumes positional arrays only. Its registry upsert, deletion of old lineage, and individual insertions are separate SQL calls. Failure after deletion can leave a published row with incomplete ancestry.
- The direct output sink in `project.cpp`, around line 1257, consumes named objects only. Core row and column binding construct malformed lineage arrays in `operations.cpp` around lines 355 and 412. Several expressions look up `result_id` twice as their own fallback.

**Implementation**

1. Use one manifest representation for every producer. For example, an upstream output called `featuresTable` bound to `inputTable` contributes `{"result_id":"r1","source_port":"featuresTable","target_port":"inputTable"}` to `provenance.lineage_inputs`. Prefer the actual source output port. A contract alone may identify several outputs. Record separate edges when one result is connected twice. For table-valued parameter bindings, trace the original source connection before the parameter becomes a bare reference.
2. Centralize construction and validation in project-owned code shared by built-in and dynamic producers. Zero inputs produces an empty array. Reject malformed edges with a useful error. Do not fabricate a result ID for literal parameters or success signals.
3. Use one DuckDB transaction for registry upsert and lineage replacement. Check the existing `ProjectTableStore::transaction` and `append_artifact_lineage` implementations. The filesystem rename and DuckDB transaction are separate durability boundaries. Document what is visible if registration fails after rename and ensure retry registers the same result once. Cache lookup and inventory must agree on its availability.
4. Write the canonical format on all new publications. Check how cached historical manifests reach registration before changing the reader. For an incompatible stored result, use the project’s stale-result/rerun policy with an actionable message. Avoid a second parser or rewriting historical stores.

**Acceptance** — Extend `artifact_publication_contract.cpp`, `mixed_domain_workflow_artifact_contract.cpp`, and the generic binding contract. Verify actual `RESULT_LINEAGE` rows for table and JSON outputs, two source ports, an empty source set, and two edges from one source. Register twice and inject an invalid edge during replacement. The previously committed graph must survive the failed transaction. Verify the same ancestry after reopen and on downstream invalidation.

**Progress** — Result-manifest registration validates canonical object-shaped lineage edges before opening a transaction, then performs registry upsert, old-edge deletion, and replacement inserts within one project-table transaction. A new batch registration API makes several outputs atomic together. The service uses it for all outputs from one detailed operation, for standalone operations, and for the workflow’s pipeline-mode output set. In detailed/standalone mode, a registration failure also removes that run’s unregistered store payloads; failed or cancelled workers remove only payloads carrying their unique run ID. Pipeline payloads remain on disk for inspection if final registration fails. The mixed-domain workflow contract forces a replacement failure during lineage insertion and verifies the previous registry and lineage remain intact. It also supplies a two-output batch where the second output violates lineage uniqueness and confirms the first output was rolled back. Separate result-store coverage verifies cleanup is scoped to one run. The artifact-publication contract now verifies JSON output ancestry with two distinct target edges from the same source result and verifies an input-free table output has no fabricated lineage. The contract replaces lineage with distinct source ports, reopens the project, confirms both edges persist, and checks fresh, cached, and reopened connected Arrow-table executions preserve identity. Invalidation forces both connected operations to rerun. Arrow tables are published tabular payloads in the result store; they are not physical DuckDB result tables. `bind_table_columns` therefore concatenates columns by row position after equal-row-count and unique, non-empty header validation. The focused artifact-publication, mixed-domain, result-store, and service builds pass.

## 5. Make generic table operations consume Arrow result data

**Source evidence** — Published table results are Arrow IPC data in the result store, with opaque `result_ref` handles used for service/worker access. They are not DuckDB tables. `bind_table_rows` and the previous `bind_table_columns` implementation incorrectly used SQL `DESCRIBE` and queries over a result reference. Tables are generic tabular data and their semantic structure may differ by domain.

**Implementation**

1. Implement row binding as vertical concatenation of Arrow batches after exact schema comparison. Keep source row order, bounded reads, cancellation checks, and output abort on failure.
2. Implement column binding as horizontal concatenation by row position. Require equal published row counts, preserve every input column and its exact Arrow type, and reject empty or duplicate column names across the combined schema. Do not accept row keys, match keys, reorder rows, join, query DuckDB, or copy results through JSON. Read aligned bounded logical row windows from both Arrow IPC results and emit a batch containing the left columns followed by the right columns. Handle differing IPC record-batch boundaries by coalescing slices to the same logical window.
3. Scope required arguments to each proxy method. Audit `describe`, `has_table`, `count_rows`, `append_rows`, `query`, `execute`, and `write_query_result` for live producers. Replace obsolete row-based paths at the owning operation before deleting them. Preserve supported CSV read/export entry points and direct embedded APIs that still have callers.
4. Keep SQL schema conversion only at operations that actually ingest SQL-derived data, such as CSV import. For Arrow-to-Arrow binding, use published descriptors and Arrow schemas directly so decimal scale, timestamps, lists, nulls, and physical types are preserved without a DuckDB mapping layer.

**Acceptance** — An actual packaged run must read CSV, bind two file-backed results vertically and horizontally, and export the expected row count, positional row pairing, column order, values, and lineage. For horizontal binding verify unequal row counts fail, duplicate headers fail, input ordering is preserved, distinct column types remain unchanged, differing Arrow record-batch boundaries still align correctly, and zero-row results retain the declared schema. Exercise CSV quoting for commas, embedded quotes, and newlines. Preserve any existing user destination if export fails partway.

This matches generic table semantics: append columns in order after validating equal row counts and unique header names. Table references now carry result IDs without a DuckDB table locator. Project result metadata no longer declares, reads, or writes `physical_table`, and result clearing no longer scans or drops generated `ARTIFACT_*` tables. The service publishes opaque `result_ref` values to dynamic plugin inputs. A fresh packaged MCP workflow completed with two CSV readers, column binding, and CSV export; MCP `request_result` returned two positional row pairs (`alpha/1.25/first`, `beta/2.5/second`) with expected schema order, and the CSV matched. The output sink contract verifies default extensions and preservation of provenance/workflow revision. The ontology describes horizontal concatenation; generic binding has no parameters. The Arrow writer and publication validator share a strict semantic-to-Arrow schema mapper. Catalogue generation conforms. Full Windows package creation passed all 44 CTests, the frontend suite passed 29 files/111 tests, and `sfdev test browser` passed against the packaged app. The result-store Arrow contract now publishes and rereads decimal, timestamp, binary, and integer-list columns, asserting exact IPC schema and values; `sfdev build backend --target streamfind_result_store_arrow_contract` and its focused CTest pass.
